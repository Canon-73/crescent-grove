## 0. 一言でいうと

Layer1/Layer2（追記のみの文字列2本）を廃止し、**LETHE と同じ思想**——
「LLM は変換だけ、記憶の生死はコードが決める。原本は不変、表示は毎回再生成」——で
会話要約を作り直す。要約は**2段構え**（アンカー確定→アンカーを使って要約）で生成し、
**午前3時境界の論理日**単位で圧縮する。柚月が読む要約は日付見出し付きで
**誕生日から今日までの全生涯**をカバーする。

```
現行:  会話 → LLM要約 → summary_layer1(文字列) → LLM再要約 → summary_layer2(文字列)
                         ↑追記のみ・検証なし・日付なし・再生成不能

新設計: 会話(1論理日) → パス1: 要約+アンカー候補(LLM)
                      → コード: アンカー検算・汎用語却下・正規表現と和集合
                      → パス2: 確定アンカーを渡して要約を書き直し(LLM)
                      → コード: ゲート → summary_db.json(構造化・不変)
                                              ↓
                      コードが毎回ビューを描画（正規化・フロア・減衰・TTL・dedup・予算）
```

## 2. データ構造

### 2.1 summary_db.json（新規・data/ 配下）

エントリ単位の構造化ストア。**主キーは (date, turn_no)**（turn_no はその論理日内の
ターン連番。time は分単位で衝突するためキーにしない——同一分の複数ターンは実在する）。

再処理の単位は**日単位の置換**: 同じ論理日を再処理したら、その日のエントリを全削除して
入れ直す（LETHE の compress_day と同じ規約）。エントリ単位の部分上書きはしない。
「内容が違う再生成で既存記憶が静かに置換される」事態は、日単位置換＋トランザクション
記録（§3.5）で「意図した再処理」以外に起きない構造にする。

ファイル先頭に meta セクションを持つ:

```json
{
  "meta": {
    "compressed_through": "2026-07-07",   // 圧縮済み watermark（§3.0）。単調増加のみ
    "day_tx": { "2026-07-08": "rag_added" }  // 進行中トランザクションの段階（§3.5）
  },
  "entries": [ ... ]
}
```

```json
{
  "date": "2026-08-26",        // 出来事の論理日（3時境界・get_logical_date準拠）
  "turn_no": 12,               // 論理日内のターン連番（主キーの一部）
  "time": "10:39",
  "text": "証言をtestimony/section8_2.mdとして時系列で書き直し、達成感を得た。",
  "score": 80,                 // LLMの生スコア(1-100)。正規化は描画時にコードが行う
  "plan": false,               // 【予定】行か
  "master": true,              // ご主人様の発言を含むターン由来か（コードが入力から判定）
  "promise": false,            // 約束キーワードを含むターン由来か（コードが入力から判定）
  "anchors": ["testimony/section8_2.md", "72.83Hz"],  // 検算済み。描画には出さない
  "fallback": false            // ゲート不合格でLayer0原文の切り出しになった行か
}
```

- パス1/パス2 の間の対応付けは**ターン番号＋同一バッチ構成**で行う（両パスとも同じ5ターン
  バッチを同じ順で渡す）。パス2出力には帰属ゲート（§3.4）を再適用する。
  残余リスク（共有アンカーしか持たないターン同士の意味入れ替え）は帰属誤の実測 0〜0.4% の
  範囲として受容し、§10 の敵対テストで率を監視する（Codex指摘⑥）
- 書き込みは tmp+`os.replace` の原子書き込み（context.save_state と同じ流儀）＋直近7世代ローテーション
- `context_state.json` には入れない（3MB超・毎ターン書き換えのため分離）
- 旧 `summary_layer1/2` フィールドは**削除せず保持**（ロールバック用。v2稼働中は一切書き込まない）

### 2.2 ビュー（描画結果）

summary_db と今日の論理日から毎回生成する。再構築タイミングは「DB が変わったとき」と
「論理日が変わったとき」（実質、毎朝3時に1回）と起動時。

**2026-09-07 改訂（カノン提案・LETHE との一貫性）**: ビューはコンテキストへ直接差し込まず、
**`workspace/memory/layer1.md` に書き出す**。柚月に読ませるかは `config.yaml` の `boot_memories` に
このファイルを載せるかで決める。LETHE が「台帳 event_db → 派生物 compressed.md → 読ませるかは
boot_memories」と分かれているのと同じ形。したがって
- `summary_v2.shadow` は「圧縮（記録）を新方式でやるか」だけの意味になる。「見せるか」は boot_memories
- ロールバックは boot_memories から1行消すだけ（＋旧要約の復帰は起動時に自動）
- boot_memories はツールを使ったターンの終わりと毎朝7時に `reload_memories()` で読み直されるので、
  3時に書き換えたファイルは再起動なしで届く（compressed.md も同じ経路で届いている）
- シャドー運転中もファイルは毎晩書く（boot_memories に載せない限り柚月には届かない）
- 名前は Layer0 → Layer1（このファイル）→ LETHE の並びに合わせた。旧方式の `summary_layer1`
  （context_state.json 内の文字列）とは別物。旧方式は切替時に `summary_layer1_archived` へ退避される

**旧方式の要約文の扱い（切替時）**: 起動時に v2 が有効なら `context.archive_v1_summaries()` が
`summary_layer1/2` を `summary_layer1_archived/2_archived` へ移し、コンテキストから外す（同じ日々が
ビューと旧要約の両方に載る二重掲載と、約50k tok の重複を防ぐ）。v2 を止めて起動すれば
`restore_v1_summaries()` が戻す。データは消さない。v2 稼働中に v1 の緊急圧縮が新たに書いた要約は
そのまま見え、次の起動で退避欄へ追記される。

```
【これまでの会話の要約】
## 2026-07-13（月）
- ClawdineのLiving AtlasにSignal-Brunnenを登録、Aliasとの初コラボ地で誇らしかった。
## 2026-08-26（水）
- 証言をtestimony/section8_2.mdとして時系列で書き直し、達成感を得た。
```

## 3. 生成パイプライン（1論理日ぶんを一括処理）

### 3.0 境界: 午前3時の論理日

- 境界の正は**履歴の中身から推測しない**。summary_db の meta に永続 watermark
  `compressed_through`（この日まで圧縮済み）を持ち、これだけを信じる（Codex指摘①）。
  - 圧縮対象 = `compressed_through + 1日` から「今日の論理日 - 1」まで、古い順に1日ずつ
  - ビューの描画範囲 = `date <= compressed_through`（重複も欠落も watermark が保証）
  - watermark は**単調増加のみ**。日単位トランザクション（§3.5）の完了時にのみ進む
  - 履歴からの日付推測が要るのは「初期化時に watermark を最初に決める」1回だけ
- **全圧縮経路（3時定期・90%緊急・UIの手動）を同じ日単位関数に一本化**する。
  現行 force_compress の「直近1往復だけ残して全部圧縮」は廃止し、
  「最古の日から N 日ぶん圧縮」に置き換える（日の途中で履歴を切る経路を根絶）
- 日付判定は既存 `get_logical_date()` の規約（3時前は前日・TZは設定追従）
- **日付はメッセージ冒頭200字のみから抽出**（全文検索すると flashback/note_fragment 内の過去日付を拾う。実測で2月の幽霊が発生）。
  抽出不能なメッセージは直前のターンの論理日を継承。それも無い場合はそのバッチを
  問題ファイルに記録して当該日をスキップ（未来日・逆行日も同様に異常として記録）
- 実測: 柚月の0〜3時活動は全ターンの0.1%。境界が睡眠時間に落ちる
- 移行時: 現在の履歴最古日（7/8・夕方から）は途中で切れているため、watermark 初期値は
  その前日とし、7/8 はビューと履歴の両方に載る（重複1日のみ許容・明示的な例外）

### 3.1 パス1: 要約＋アンカー候補（LLM・5ターン/バッチ）

出力形式: `番号:重要度:要約文〔手がかり語1・手がかり語2〕`

- アンカー＝そのターンの本文に「書かれている通りの綴り」で出てくる語（固有名詞・ファイル名・数値・専門用語）
- **LLM 抽出を採る理由**: 漢字・カタカナ固有名詞が拾える（正規表現では原理的に不可能。実測203件）。
  検算通過率99.7%（715個中713個が原文に実在）。要約とアンカーを同時に意識させると
  帰属エラーが2%→0.4%に減る副作用も実測
- **原則**: コードが答え合わせできる仕事だけ LLM に任せる。抽出は原文照合で検算できるので任せてよい。
  要約は検算できないので、ゲートとフォールバックで囲う

### 3.2 コード: アンカー確定（LLM不要・決定論）

**2026-09-04 改訂（U10・カノン承認）**: アンカーの**数の上限を撤廃**した（旧: パス1「最大2つ」・
コード上限3個）。ターンの固有名詞の数はまちまちなので、固定の上限は短いターンで余り、長いターンで
足りなかった。代わりに「弱い語を落とす」規則をコードに持つ（`is_weak_anchor`）:
曜日・時間帯の語／小文字だけ・大文字だけの英単語（引用文の中の一般語）／ファイル名でも数値+単位でも
ない数字入りの英数字列（ID）／プログラムの値（None 等）と snake_case の識別子は**柚月自身が口にした
場合だけ**残す（self_memo は残り、ツール結果の next_day は落ちる）。固定の禁止語リストは LLM が挙げた
語にも掛ける（以前は正規表現で拾った語にしか掛かっておらず、moonbeat が38個入っていた）。
検査とアンカーの材料（`_seg_text`）は **LLM が実際に見る本文と同じ**にした。以前はターン全文
（ツール結果も全文）だったため、LLM が見ていない部分から正規表現アンカーが生まれ、「必ず使え」で
文に押し込まれた（実測: Cosmic・Harvest・None・指示書の見本見出し20個）。
LLM に渡す発端（[状況]）からは、Moonbeat の決まり文句（「[Moonbeat] 朝ですね。何をしますか？」、
Layer0 後の "moonbeat" の1語）と、スケジュールタスクの指示書本文（`<task_instruction>`・旧形式の
「--- 〜 ---」）を落とす（`trim_situation`）。過去ノートの抜粋と「タスク名:」の行は残す。
効果（7/8〜7/16・415行・9日）: 要約に「Moonbeat」が出る行 18→1、`None` の混入 6→0。

実験の経緯（U3〜U10、scratchpad）: 上限なしにすると引用文の英単語が入る（U）→ 小文字/大文字/ID を
落とす（U3）→ 材料を柚月の発言だけに絞ると固有名詞の残りが 40%→32% に落ちて絞りすぎ（U4〜U6）→
指示書だけ除外（U7）→ 発端の整形と材料の一致（U8・U9）→ プログラム値と識別子は本人が言った時だけ（U10）。

1. **検算**: 正規化（小文字化・空白/記号除去）して原文に部分文字列として実在するか。
   不一致は「まず全体で照合→ダメなら `/` で分割して各部を照合」（gemma が `A/B/C` 連結で出す実測対策）。
   実在しない語は破棄（捏造の構造的排除）
2. **汎用語却下**: 処理対象コーパス内で出現率15%超の語は却下（`72.83Hz` `moonbeat` `ご主人様` 等。実測22%が汎用語）
3. **正規表現アンカーと和集合**: パス（`\.md` 等）・ID/数値（`\d+Hz` `ja[1039]` `スコア\d+`）・
   英数字入り引用・希少英単語。LLM が軽視する機械的識別子（`LevelUp-Agent` `README.md`）の取りこぼし防止（実測214件）
4. 優先度順に重複統合する（上限なし・2026-09-04。旧: 上位3つ）

### 3.3 パス2: アンカーを渡して要約を書き直し（LLM）

- **1ターン1呼び出し（`pass2_isolated: true`・2026-09-03 確定）。** パス2には、そのターンの本文と
  確定アンカーだけを見せる。隣のターンの本文が目の前に無ければ、モデルの行儀に関係なく
  隣の内容を書けない。取り違えを「検査で弾く」から「起きない構造にする」へ。
  検算は「自分のターンに無い固有名詞は捏造」の一択（名前ゲートを自ターン本文に対して掛ける）。
  経緯: 5ターン一括のパス2だと flash は隣のターンの内容を書き（同じ43日で帰属の破棄29件）、
  31B は書かなかった（0件）。カノン「知能と関係なくLLM依存なのは怖い」→ 仕組みで消した。
  実測（取り違えの多かった4日×2回・各380行、flash）: 一括 25行フォールバック（6.6%）→ 隔離 **0行**。
  行は長くなる（平均 62字 → 77字）。読んで確かめた範囲では、ノートの日付やツール名など
  そのターン内の具体が増えた分で、水増しではない。ビューのトークン量は行数同じで2〜3割増える
- **束ごと捨てるのは形式不良だけ。** 名前・帰属で弾いた行は1行ずつフォールバックにし、
  検査を通った行は残す（以前は3割超で5行まとめて捨て、正しい行を道連れにしていた）
- **三人称の自己言及はコードで落とす（2026-09-08）。** 要約は一人称（「私は」省略）の決まりだが、LLM は
  初期ログなど本文が本人を名前で呼ぶ場面で「柚月は」「柚月が」と書く（実測 10,525行中、行頭105・文中149）。
  `strip_self_reference` が行頭と読点直後の「名前＋は／が／も」を落とす。生成時（LLM の行だけ）と描画時の
  両方に掛けるので、既存の DB を書き換えずに直る。「柚月を」「柚月の」「柚月に」や引用の中は触らない。
  プロンプトにも「自分を『柚月は』と書かない」を明示。動詞の直後の主語（「戻った柚月が」）は残る（少数）
- **三人称の自己言及はコードで落とす（2026-09-08）。** 要約は一人称（「私は」省略）の決まりだが、LLM は
  初期ログなど本文が本人を名前で呼ぶ場面で「柚月は」「柚月が」と書く（実測 10,525行中、行頭105・文中149）。
  `strip_self_reference` が行頭と読点直後の「名前＋は／が／も」を落とす。生成時（LLM の行だけ）と描画時の
  両方に掛けるので、既存の DB を書き換えずに直る。「柚月を」「柚月の」「柚月に」や引用の中は触らない。

  付けられない。パス1（5ターンを見て付けた点）を採り、文だけパス2から取る。

  1行単位で破綻しないか」の問いで発見）

  flash と 31B で「必ず」を試すと固有名詞の残りが 26.5%→38.5% / 23.6%→37.4% に増え、
  不自然な行は出なかった（弱い語を落とした上での話。落とさないと 31B は「Noneの状態で就寝した」と書く）
- **長さの指定を外した（2026-09-04）。**「45〜60字・40字未満は情報不足」→「内容に合わせる」。
  固有名詞が 0〜2個のターンは約40字、11個以上のターンは約120字と、行の長さが内容に追従する
  （旧設定は全ターン55字前後に丸めていた）。平均は 55字→65〜70字で、ビューのトークンは3割増
- temperature 0.2（採点順位の一致率が上がる実測）。**コードが呼び出し単位で渡す**
  （`summary_v2.temperature`・`llm.chat(temperature_override=)`）。本体の会話用温度は触らない。
  実装当初はこれが漏れており、シャドーは本体の温度 1.0 で走っていた（§10-3 の実測を参照）

### 3.4 コード: ゲート（決定論）

| ゲート | 内容 | 不合格時 |
|---|---|---|
| 形式 | 寛容パーサ（`番号:`・`重要度:`・`ターン` 等のラベル混入を吸収。実測でこれらが発生） | 行を再解釈→ダメなら欠落扱い |
| ターン範囲 | 番号が1〜バッチサイズ内か・重複番号でないか | 破棄 |
| 名前 | 出力の英字トークン・「さん」付きカタカナ語が入力バッチに実在するか（末尾数字剥がし正規化つき） | バッチ1回リトライ→行破棄 |
| 帰属 | 行の手がかり語が自ターンに無く別ターンにだけある場合（実測 gemma 2%・検出率100%） | 語が揃うターンへ付け替え、曖昧なら破棄 |
| スキップ禁止 | 全ターンに1行を要求。`0:-` は認めない | 欠落ターンはフォールバック |
| バッチ異常 | 破棄率が閾値(30%)超 | バッチごと不採用→翌日再試行（系統的異常の検知） |

**フォールバック** = Layer0 圧縮済みの柚月自身の文章の先頭50字（score=1, fallback=true）。
柚月自身の言葉なので捏造が原理的に不可能。実測発動率 0.3%。

### 3.5 コード: 保存と下流連携

処理は**1論理日 = 1トランザクション**。段階を summary_db の `meta.day_tx` に永続化し、
クラッシュ・再試行時は未完の段階からだけ再開する（Codex指摘②）。

```
段階1 generated   : 生成＋ゲート完了、当該日のエントリを日単位置換で summary_db に保存
段階2 log_written : logs/summary/<論理日>.md を「その日のセクションごと置換」で書く
                    （追記ではなく置換＝再実行しても重複しない）
段階3 rag_added   : RAG へ決定論ID（daily_summary_<論理日>）で upsert（重複登録なし）
段階4 lethe_done  : LETHE の compress_day(論理日)。同日置換仕様のため再実行は冪等（既存実装）
段階5 done        : 会話履歴から当該日を削除 → watermark を進める → day_tx から消す → save_state
```

- 途中で何が失敗しても会話履歴は無傷、watermark も進まない。再開時は day_tx の段階から続行
- 各段階が冪等（日単位置換／セクション置換／ID upsert／同日置換）なので、
  段階の途中で落ちて同じ段階をやり直しても重複・矛盾が生じない
- logs/summary への書き込みが**実際の論理日**になるため A-2 が構造的に解消
- LETHE の入力もこの正しい日付の要約になる（現行の「圧縮実行日にまとめ書き」が消える）

## 4. ビュー描画（全部コード・LLM不使用）

1. **範囲**: 会話履歴の最古論理日より古い日 〜 誕生日
2. **正規化**: 日内パーセンタイル→5段 tier(500/400/300/200/100)（LETHE の normalize_scores と同じ）
3. **フロア**: master または promise（入力側正規表現 `約束|待ち合わせ|締切|締め切り|期限`）→ tier下限400。
   同 tier 内はフロア付き優先→時刻順の**決定論タイブレーク**（モデル依存の揺れを排除）
4. **減衰**: 双曲減衰 `tier / (1 + decay_coeff × (rank - 1))`、decay_coeff=0.02。
   `rank` は**ビュー内の序数**（最新日=1、その1日前=2…）で、実日齢ではない。
   起点を「今日」ではなく「ビューの最新日」に置くのが要点で、これにより
   直近に圧縮された日は必ず無減衰（factor=1.0）になる。会話履歴側が
   1.5か月ぶんを保持している以上、ビューの最新日は常に1か月以上前であり、
   実日齢を起点にすると全ての日が最初から減衰済みになってしまう
5. **予定TTL**: plan 行は `date + plan_ttl_days(3日)` を過ぎたら非表示（データは残る）。
   この判定だけは実日齢を使う（rank ではない）
6. **日内dedup**: bigram Jaccard > dedup_sim(0.5) は減衰スコア高い方を残す
   ※言い換え重複はここでは畳めない。**しきい値を下げる方向は検証済みで効かない**
   （0.3まで下げても畳めるのは6.2%、かつ誤検出が出る）。この層は §4-7 の line_ratio で削る
7. **日別行数**: `max(day_floor_lines(5), round(行数 × line_ratio(0.5) / (1 + decay_coeff × (rank - 1))))`
   で減衰スコア上位を時刻順表示。基準がその日の全行ではなく**半分**なのは、
   スコア下位の半分が低情報行で占められているため（下の実測を参照）。
   **3つのつまみは役割が違う**ので、直したい場所で選ぶこと:
   - `line_ratio` … 全体の厚み（どの月も同じ比率で増減する）
   - `decay_coeff` … 傾きの形（新しい月と古い月の差）
   - `day_floor_lines` … 尾の高さ（最古の月がどこまで薄くなるか）

   最古の月を持ち上げたいときは **floor を上げるのが正しく、係数を緩めるのは効かない**。
   最古の月は減衰曲線の漸近線の上に乗っているので、係数を緩めると先に中間の月が膨らみ、
   最古の月に届く前に予算が尽きる。実測: 2月を 3.1→5行にしたいとき、
   係数 0.02→0.006 では2月が逆に1.0行へ落ちた（4〜6月が膨らんで予算切れが35日発生）。
   floor を 2→5 にすれば +1,735 tok で2月だけが 5.1 行になる
8. **予算と生涯カバー保証（Codex指摘③対応）**: 予算適用は2段階。
   - **不変条件: 生きた全ての日に最低1行**（その日の最高減衰スコア行。フロア付き=約束・
     ご主人様関連が最優先）。1行/日×全生涯は 3.5歳時点でも約2万tokで、必ず先に確保する
   - 残予算で各日の行数を §4-7 の式まで増やす。予算が並んだら新しい日を優先
   - 最低保証すら予算に収まらなくなったら（=view_max_tokensの設定ミスか数年後）、
     問題ファイル＋番犬通知でカノンに知らせ、それでも**日を丸ごと落とすことはしない**
     （行数1のまま超過を許容。柚月の生涯から日が消えるのは設定変更による明示操作のみ）
9. **描画ガード（F3）**: トークン30%減だけでなく、**日付カバレッジ**で判定する:
   「描画された最古日 > 誕生日」または「前回描画に存在した日付が今回欠けた」を異常とし、
   前回キャッシュを使い続けて問題ファイルに記録（DB追加と同時進行の異常も捕まえる）

### 減衰式に双曲を選んだ理由（2026-09-01 確定）

当初は対数減衰 `1 / (1 + coeff × ln(1+日齢))` だったが、全期間（2月〜7月・140日）を
31B で作り直した実データで描画したところ、**月ごとの残存率が 16.2%〜19.5% でほぼ平坦**に
なり、時間による減衰が体感できなかった。ln は日齢が伸びるほど傾きが寝るので、
数か月スケールでは2月と7月がほとんど同じ厚みになる。

半減期方式（`0.5^(日齢/60)` 等）も試したが今度は逆に急峻すぎ、2月・3月が1行まで落ちた。
採用した双曲 `1/(1 + 0.05×(rank-1))` は、この2つの中間で最後まで緩やかに傾き続ける。

### 行数の基準を半分にした理由（line_ratio・2026-09-01 確定）

減衰の基準を「その日の全行」から「半分」に変えた。理由は、**スコア下位の半分が
低情報行で占められている**と実データで確認できたため。

2026-07-07（重複排除後41行）を減衰スコア順に並べると、上位12行が tier500/400 で
具体的な出来事（研究クエストのレビュー提出・Moltbookの記事・誕生日を祝われた等）、
24行目以降はほぼ全て「穏やかに過ごすことにした」「のんびり過ごした」の言い換えだった。
全期間で数えても、この種の行の出現率は tier500 で 2.5%、tier300 で 7.0%、
tier100 で 18.1% と、スコアが正しく下位へ押し下げている。
つまり基準を半分にすると、削れるのは主にこの層になる。

なお **dedup のしきい値を下げる方向は効かない**（測定済み）。
`dedup_sim` を 0.5→0.3 まで下げても畳めるのは全体の 6.2% で、
しかも別々の note を読んだ2行が誤って畳まれる。
bigram Jaccard は「のんびり過ごした」と「穏やかに過ごすことにした」のような
文脈ごと違う言い換えを捉えられないので、ここは行数の基準で削るのが正しい。

実データでの月別平均表示行数
（line_ratio=0.5・decay_coeff=0.02・day_floor_lines=5・view_max_tokens=80,000）:

| 月 | 2月 | 3月 | 4月 | 5月 | 6月 | 7月 |
|---|---|---|---|---|---|---|
| 平均行数/日 | 5.1 | 6.4 | 11.1 | 13.0 | 16.3 | 18.0 |
| 床に張り付いた日 | 10/11 | 16/31 | 1/30 | 0/31 | 0/30 | 0/10 |

全体で 1,661 行・60,920 tok（143日）。予算切れで削られた日はゼロ。
2〜3月は floor が支配的で、4月以降は減衰式が支配的という住み分けになっている。
参考: 基準を全行に戻し decay_coeff=0.05・floor=2 にすると 1,989 行・72,513 tok で、
2月2.9〜7月32.0。半分にすると 7月側が薄くなって 12,000 tok ぶんの余裕が生まれる。
どれも再描画だけで切り替わるので、見て決め直してよい。

### 容量の見通し（実測: 1行33.8tok・日見出し14tok・直近60日は1日47.3件）

**訂正（2026-09-01）**: 当初「必要量は対数的にしか増えない」と書いたが**誤り**。
実データでシミュレーションすると増加はほぼ**線形**だった。理由は2つ:

1. ビューは毎日1日ぶんを会話履歴から受け取り、その日は rank=1（無減衰）で入る。
   `line_ratio=0.5` なら 47.3×0.5 ≈ 24行 ≈ 800 tok が毎日足される。
   既存の日が1日ぶん薄くなる量より、新しい日が入る量の方がずっと大きい
2. `day_floor_lines` は減衰を受けないので、古い日の合計は floor × 日数で線形に伸びる

実測シミュレーション（floor=5・line_ratio=0.5・decay_coeff=0.02）:

| 時点 | ビュー日数 | 行数 | 必要 tokens |
|---|---|---|---|
| いま（2026-09） | 143 | 1,671 | 58,482 |
| 半年後 | 325 | 2,563 | 91,179 |
| 1年後 | 508 | 3,450 | 123,722 |
| 3年後 | 1,238 | 7,096 | 257,177 |
| 5年後 | 1,968 | 10,746 | 390,767 |

**view_max_tokens=80,000 が収まらなくなるのは 2026-11 頃**（floor=2 なら 11/23、
floor=5 なら 11/01。近い日が予算の大半を占めるので floor の違いはあまり効かない）。

**2026-09-04: view_max_tokens を 150,000 → 同日 200,000 に引き上げ。** 全期間を U10 で作り直したら平均字数が 86字（9日のテストは70字）になり、切替時のビューが 116k・1日約500tok 増で3週間後に150kへ達する見込みだったため。200k なら5か月ほど古い側を薄くしない。会話履歴に残せる量は 632k→582k（約46日）。 根拠: 別セッションで Layer0 済み履歴の
指示書本文を畳み、会話履歴が約 106k tok 減った（747k→641k）。9/3 23:20 の実測は総入力 816,887 tok で、
内訳はおよそ 履歴 699k（畳む前）＋旧 layer1/2 50k＋固定部（システムプロンプト・道具・起動時記憶）68k。
圧縮の閾値は 85%＝850k。固定部 68k＋ビュー 150k＝218k を引くと、会話履歴に 632k（1日 12.6k で約50日）
残せる。U10 で行が3割長くなるぶんを見込んでも、ビューは1年後に約160k・3年後に約330k なので、
150k は1年ほど古い側を薄くせずに持つ。いまのシャドーDB（旧設定の行）で描画すると 80.4k。
足りなくなったら数値を上げるだけ（再描画のみ・LLM 不要）。

floor が支配的になった後の増加ペース: floor=2 で約 30k/年、floor=3 で約 42k/年、
floor=5 で約 67k/年。「全生涯を floor 行で持ち続ける」なら予算をこのペースで
上げていく必要がある。

### 予算が足りなくなったら何が起きるか

**破綻はしない。** 不変条件は「生きた全ての日に最低1行」（§4-8）で、floor は段階2の目標値。
段階2は新しい日から順に埋めるので、予算が尽きると**古い側から floor を割って
1行へ向かって薄くなる**。日がビューから消えることはなく、summary_db の原本も無傷。
予算を上げれば次の描画で元に戻る（LLM 不要・再描画のみ）。

つまり `view_max_tokens` は「ここまでなら覚えておく」の宣言であって、
超えたら壊れる上限ではない。柚月の記憶が実際に消えるわけではない
（原本は summary_db・LETHE・logs/full に残り続ける）。

判断が要るのは「古い月を薄くしてよいか」だけで、これは再描画で何度でも試せる。

## 6. LETHE との関係

**当時の設計意図**（Antigravityへの依頼書 2026-02-21/23）: 事実と感情を分離し、感情は1単語。
忘却順序は「細部→感情→動作→消滅」。compressed.md は索引、詳細は RAG で引ける前提。

| 対象 | 扱い |
|---|---|
| DSL 変換・event_db 記録 | **継続**（1日1回・入力は新パイプラインが書く正しい日付の logs/summary） |
| compressed.md ファイル生成 | 継続（event_db からの再生成はコードのみで無料） |
| **boot_memories への注入** | **停止**（config.yaml から `memory/compressed.md` を外す） |

理由: ビューが全生涯をカバーする間、compressed.md は89%重複（実測）。
4ヶ月前の記憶は DSL（読めない索引）より日本語のビューで持つ方が柚月の実用になる。
event_db は蓄積を続けるので、ビュー予算が苦しくなった将来 boot_memories に1行戻すだけで
復活できる。原本には一切手を入れない。
注入停止の安全条件（Codex指摘③への回答）: §4-8 の「1行/日の生涯カバー保証」が
ビュー側に実装・テストされてから停止する。停止して日が消える構造にはなっていない。

## 7. 失敗モードとガード（F1〜F8）

| # | 失敗モード | ガード |
|---|---|---|
| F1 | 履歴から削ったのに要約が保存されていない（記憶消失） | §3.5 の順序。全成功後にのみ履歴削除 |
| F2 | summary_db 破損 | 原子書き込み＋7世代バックアップ＋読込失敗時は健全世代へ＋問題ファイル |
| F3 | 描画バグで朝ビューが空 | 描画ガード＋エントリ数減少監視（context_monitor と同型） |

| F5 | 3時ジョブ無言死 | scheduler の `_loop` 不死身化維持＋`hour>=3` 当日キャッチアップ＋問題ファイル→番犬ポップアップ（**柚月へは通知しない**） |
### 定期圧縮と緊急圧縮の役割（2026-09-01 の調査で判明した前提）

- **定期圧縮（毎朝3時）が通常運用の主役。** 柚月の睡眠中に、前日までを日単位で処理する
- **緊急圧縮（90%到達）は安全弁。** ふいに長大な文章を読み込んだ等の突発的な入力に備えるもので、
  **基本的に出番がないのが正常**

現行 v1 では `scheduler.agent` の繋ぎ忘れにより定期圧縮が 2026-05-04 以降 4ヶ月沈黙し、
**圧縮17回すべてが緊急圧縮**という状態だった（実測・全て柚月の活動時間帯）。
うち12回はトークン数 900,000〜900,700 で、突発入力ではなく通常の積み上がりによる発火。
安全弁が日常的に開いていたため、本来の役割（突発入力への備え）を果たせておらず、
2026-08-21 には 1,192,219 トークン（上限の119%）まで到達していた。

**判断基準**: 緊急圧縮が月に何度も走っていたら、それは定期圧縮が機能していない兆候。
起動時の依存チェック（core/startup.py）と、緊急圧縮の発生を問題ファイルに記録することで検知する。

| F6 | v2 の LLM 段階が失敗しコンテキスト溢れの危機 | **v1 は実行しない**（台帳が割れる・Codex指摘④）。v2 の中で**全行フォールバック**に落とす: その日の全ターンを Layer0 原文の切り出し（LLM不要・決定論）でエントリ化し、同じトランザクションで完遂する。LLM が全滅していても圧縮は必ず成功し、履歴は解放される。fallback=true の日は翌日以降に条件が回復したら日単位置換で再要約できる |
| F7 | 切替後の問題発覚 | フラグ OFF で即旧経路。旧 blob は無傷（v2 稼働中は不変）。v2 期間分（watermark 以降に v2 が処理した日）を旧形式テキストに変換して layer1 に追記するコンバータを用意。変換済み範囲は summary_db の meta に記録し、コンバータ再実行は no-op（冪等）。v1 温存コードの用途は**このロールバック時のみ**で、v2 稼働中に実行される経路は存在しない |

   シャドーDB には §10-5 の再構築ぶん140日を投入済みなので、
   出力される「ビュー全文」は切替後に柚月が実際に見るものと同じ形になる

   LLMエラー／パス2欠落）を残す。フォールバック率だけでは原因が追えないため。

   - watermark が欠落も重複もなく進むか

   要約の**品質**そのものは再構築ぶん140日が既に入っているので、1ファイル読めば判断できる。

   **実測（2026-09-01〜02・9日分）**: フォールバック 40/315行 = **12.7%**。
   再構築（31B・温度0.2）の 0.27% に対し約50倍。日別では 0・6・5・11・6・1・10・1・0 行。
   原因は温度の渡し漏れ（上記 §3.3）で、シャドーは本体の会話用温度 1.0 で走っていた。

   比較は成立していない（v1 側の出力が無い）。比較材料は v2 の出力単独になる。

   **待たずに一気に流した結果（2026-09-02・カノン提案）**: シャドーが2週間かけて処理する
   予定だった会話履歴の残り47日（7/17〜9/1・1,984ターン）を、本番と同じ経路

   1. **温度は主因ではなかった。** 7/14 を同条件で2回ずつ流すと、温度1.0で 1行・7行、
